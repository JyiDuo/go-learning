# Go 后端接入大模型 API 与安全规范

## 一、今日目标达成
在之前的 CRUD 后端基础上，新增了 `POST /chat` 接口。用户发送一段文本，后端调用 DeepSeek 大模型 API，获取回复并返回给前端。

## 二、核心技术实现

### 1. 使用 Resty 发起 HTTP 请求
没有使用 Go 原生繁琐的 `net/http`，而是引入了第三方库 `github.com/go-resty/resty/v2`。
```go
client := resty.New()
resp, err := client.R().
    SetHeader("Content-Type", "application/json").
    SetHeader("Authorization", "Bearer "+apiKey).
    SetBody(reqBody).
    SetResult(&respData).
    Post("https://api.deepseek.com/chat/completions")
```
*   **`SetBody`**：把我们组装好的 Go 结构体自动转成 JSON 发出去。
*   **`SetResult`**：大模型返回 JSON 后，自动帮我们解析并填充到 `respData` 结构体里，省去了手动 `json.Unmarshal`。

### 2. 结构体映射（JSON 编解码）
*   **请求体 (`DeepSeekReq`)**：必须包含 `model`（如 deepseek-chat）和 `messages`（对话历史数组）。
*   **响应体 (`DeepSeekResp`)**：大模型返回的是嵌套很深的 JSON，我们只需要提取 `choices[0].message.content` 这部分。通过定义对应结构的结构体，Gin/Resty 底层会自动帮我们完成映射。

### 3. Gin Handler 层的转发
`ChatHandler` 负责接收前端传来的 `prompt`，调用 `utils.AskDeepSeek`，然后将得到的 `answer` 用 `c.JSON` 包装返回。

## 三、踩坑与异常处理记录

1. **HTTP 503 Service Unavailable**：
   - **现象**：调用接口时报错，提示 `Service is too busy`。
   - **原因**：DeepSeek 官方服务器在高峰期负载过高。
   - **解决**：不是代码问题，稍等几分钟重试即可。代码里的 `if resp.StatusCode() != 200` 成功捕获并返回了这个错误。
2. **超时问题**：
   - 本次请求耗时达到了 34.5s（大模型生成文本需要时间）。后续如果做流式输出（SSE），体验会更好。

## 四、⚠️ 核心安全规范（血泪教训）

**绝对、绝对、绝对不要把 API Key 硬编码在代码里推送到 GitHub！**
GitHub 上有无数爬虫机器人，24小时扫描 `sk-` 开头的字符串。一旦推上去，你的 Key 会立刻被盗刷，甚至导致账号被封禁。

**正确做法：使用环境变量**
```go
import "os"

apiKey := os.Getenv("DEEPSEEK_API_KEY")
if apiKey == "" {
    return "", fmt.Errorf("环境变量 DEEPSEEK_API_KEY 未配置")
}
```
*   **本地运行方式**：在终端执行 `$env:DEEPSEEK_API_KEY = "sk-你的真实Key"`，然后再 `go run main.go`。
*   以后真实生产环境，会把这些敏感信息放在服务器的环境变量或配置中心（如 Nacos、Apollo）里。
