
# Go 语言并发编程入门学习笔记

今天的学习主线是：**如何让程序同时做多件事（并发），并保证数据不出错。**

---

## 一、 等效二叉树（Channel 通信）

**核心理念：** “不要通过共享内存来通信，而要通过通信来共享内存。” 用流水线（Channel）代替抢数据。

### 1. 基础概念
*   **Goroutine (协程)：** 使用 `go` 关键字启动，开销极小，是 Go 并发的基石。
*   **Channel (通道)：** 协程之间传递数据的“管道”，使用 `make(chan 类型)` 创建。
    *   发送数据：`ch <- 变量` （把变量塞进管道）。
    *   接收数据：`变量 := <-ch` （从管道里拿出来）。

### 2. 避坑指南：`close` 与 `for range`
*   **关闭通道：** `close(ch)` 表示不会再有新数据写入了。
*   **规矩：** 只有**发送方**才能 `close` 通道，接收方绝对不能关。
*   **死锁陷阱：** 如果接收方用 `for v := range ch` 读取数据，当数据读完后，如果通道**没有被关闭**，`range` 就会一直傻等，导致整个程序报错死锁（`fatal error: deadlock`）。
*   **黄金法则：** 写数据的协程在写完最后一条数据后，必须调用 `close(ch)`，这样接收方的 `for range` 才能正常结束。

## 二、 互斥锁（Mutex 同步）

**核心理念：** 当不需要通信，而是要**保护共享数据**（比如全局变量、Map）不被多个协程同时修改时使用。

### 1. 基本用法
```go
var mu sync.Mutex // 声明一把锁
mu.Lock()         // 上锁（只有一个人能进）
// ... 修改数据的代码 ...
mu.Unlock()       // 解锁（下一个人可以进）
```

### 2. 进阶技巧：`defer` 解锁
```go
func (c *SafeCounter) Value(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock() // 延迟解锁
    return c.v[key]
}
```
*   **为什么要用 `defer`？** `defer` 保证在函数 `return` 退出前，锁一定会被解开。哪怕函数中间发生了 panic 崩溃，锁也能释放，防止死锁。

### 3. 初始化陷阱
*   声明 `var m map[string]int` 只是空指针（nil），直接赋值会 panic。
*   必须使用 `make(map[string]int)` 真正分配内存后才能使用。
*   结构体字面量初始化：`SafeCounter{v: make(map[string]int)}`，这样既创建了对象，又初始化了内部字段，一步到位。

## 三、 网络爬虫（并发实战）

**核心理念：** 结合 Goroutine、Mutex、Channel 完成实际任务，同时解决“主协程提前退出”的问题。

### 1. 核心难题：主协程不等人
*   在 `main` 函数中启动了一堆 `go` 协程后，如果 `main` 执行到了结尾，**程序会直接退出，所有还没跑完的协程都会被强制杀掉。**
*   **解决办法：** 使用 `sync.WaitGroup`（等待组），相当于一个计数牌。

### 2. WaitGroup 的三步曲
1.  `wg.Add(1)`：启动新协程前，告诉计数器“加 1 个任务”。
2.  `defer wg.Done()`：协程内部，任务结束时，告诉计数器“减 1 个任务”。
3.  `wg.Wait()`：在主函数最后调用，主程序会一直卡在这里，直到计数器归零。

### 3. 并发安全字典（防止重复爬取）
*   如果在多个协程中直接读写同一个 Map，程序会直接崩溃（`concurrent map writes`）。
*   **解决方案：** 将 Map 和 Mutex 封装在一起。
```go
type SafeCache struct {
    mu   sync.Mutex
    seen map[string]bool
}
```

### 4. 抽象接口（Interface）
*   只定义行为，不管具体怎么实现。例如 `Fetcher` 接口规定必须有个 `Fetch` 方法。
*   底层可以使用 `fakeFetcher`（假数据）来实现这个接口，方便本地测试，不需要真的去联网。

---

## 💡 总结：Channel vs Mutex 怎么选？
*   **用 Channel**：当多个协程需要**传递数据**、排队处理时（像传送带）。
*   **用 Mutex**：当多个协程需要**修改同一个共享状态**时（像上厕所锁门）。
*   **用 WaitGroup**：当你需要**等待**一组并发任务全部执行完毕时。
