# Gin 进阶：企业级分层架构与 Memo API 实战

## 一、为什么要用“分层架构”？
如果所有的代码（路由、解析参数、业务逻辑、存数据）全塞在 `main.go` 里，代码会变成一团乱麻（面条代码），难以维护。
标准的后端工程结构应将职责拆分：
1. **Router（路由层）**：负责把请求分发到对应的处理函数。
2. **Handler（控制层）**：负责接待客人（接收参数、解析 JSON、返回响应）。
3. **Model（数据层/业务层）**：负责后厨炒菜（核心业务逻辑、管理数据结构、操作数据库）。

## 二、项目目录结构规范
```text
test02/
├── main.go          # 程序入口，启动服务
├── router/
│   └── router.go    # 路由注册与分组
├── handler/
│   └── memo.go      # 控制层：处理 HTTP 请求
└── model/
    └── memo.go      # 数据层：定义结构体，管理内存数据
```

## 三、核心代码拆解

### 1. Model 层（数据与逻辑）
*   定义备忘录结构体：
    ```go
    type Memo struct {
        ID      int    `json:"id"`
        Content string `json:"content"`
    }
    ```
*   用全局切片 `var MemoList []Memo` 充当临时数据库。
*   **自增 ID 逻辑**：`newID := len(MemoList) + 1`。保证每一条新数据都有唯一的身份标识（主键），方便后续的删除和修改。

### 2. Handler 层（控制层）
*   定义一个专门接收前端 JSON 的模具结构体（如 `CreateMemoReq`）。
*   核心函数：`c.ShouldBindJSON(&req)`。
    *   把前端发来的裸文本解析并套入模具。
    *   如果前端数据格式错误，`err != nil`，必须立即返回 `400 BadRequest` 并 `return` 退出，防止程序崩溃（防御性编程）。
*   调用 `model.CreateMemo()` 处理业务，用 `c.JSON(200, ...)` 将结果转成 JSON 返回。

### 3. Router 层（路由层）
*   使用 `r.Group("/memos")` 进行路由分组，让代码结构更清晰。
*   将 GET 和 POST 请求分别绑定到 Handler 层的具体函数上。

### 4. main.go 入口
*   `r := router.SetupRouter()` 获取路由实例，`r.Run(":8080")` 启动服务。

## 四、踩坑与排错记录
1.  **400 错误（内容格式不对）**：说明 `ShouldBindJSON` 解析失败。原因是前端（Apifox）没有在 `Body` 里选择 `JSON` 格式并填入合法的 JSON 数据，或者发了 GET 请求却勾选了 Body。
2.  **`The system cannot find the file specified`**：在终端运行 `main.go` 时，没注意路径。因为 `main.go` 在 `test02` 目录下，必须先 `cd test02` 再 `go run main.go`。

## 五、现阶段代码的致命弱点
目前数据存在全局切片 `MemoList` 中。**只要重启程序（Ctrl+C），内存就会清空，数据全部丢失。**
**下一步计划**：引入 GORM 框架和数据库，实现数据持久化。
