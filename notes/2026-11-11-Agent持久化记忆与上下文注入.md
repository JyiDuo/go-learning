# 核心实战：Agent 持久化记忆与上下文注入

## 一、为什么需要持久化记忆？
昨天我们用 Eino 跑通了 Function Calling，但每次请求的 `messages` 数组里只有当前这一句话。
一旦用户开启新对话，或者服务重启，AI 就会变成“金鱼记忆”，完全忘记刚才聊过什么。
为了解决这个问题，我们必须**把聊天记录存入数据库**，并在每次请求大模型前，把历史记录查出来“注入”到上下文中。

## 二、数据库设计与 GORM 操作

### 1. 聊天记录模型
在 `model/chat_history.go` 中定义：
```go
type ChatHistory struct {
	gorm.Model
	UserID  uint   `json:"user_id"`  // 属于哪个用户（数据隔离）
	Role    string `json:"role"`     // 角色：user 或 assistant
	Content string `json:"content"`  // 聊天内容
}
数据隔离：通过 UserID 区分不同用户。张三的 AI 绝不会记得李四说过的话。

2. 核心查询逻辑
go
// 按 ID 倒序拿最近的 N 条
DB.Where("user_id = ?", userID).Order("id desc").Limit(limit).Find(&chats)

// 反转切片
for i, j := 0, len(chats)-1; i < j; i, j = i+1, j-1 {
	chats[i], chats[j] = chats[j], chats[i]
}
为什么要 Order("id desc")：保证拿到的是最新的 N 条，而不是最老的 N 条。

为什么要反转：数据库查出来是倒序的，但大模型处理上下文必须按时间正序（先问 -> 先答 -> 后问 -> 后答）。反转后，才能符合人类的对话逻辑。

三、Handler 层的“记忆注入”流程
1. 注入历史记录（核心）
go
history := model.GetRecentChats(userID, 10)
for _, chat := range history {
	role := schema.User
	if chat.Role == "assistant" {
		role = schema.Assistant
	}
	messages = append(messages, &schema.Message{
		Role:    role,
		Content: chat.Content,
	})
}
从数据库拿到数据后，必须做一个类型转换：把数据库里的字符串 "user" / "assistant" 转换成 Eino 能识别的 schema.User / schema.Assistant 枚举。

2. 拼接当前问题并落库
go
messages = append(messages, &schema.Message{Role: schema.User, Content: req.Prompt})
model.SaveChat(userID, "user", req.Prompt) // 先存库，防丢失
把用户当前说的话追加到历史记录末尾，组成完整的上下文，然后发给大模型。

3. AI 回复后的收尾（极其容易忘！）
如果触发了工具调用，必须等第二次大模型总结完，再把结果 SaveChat(userID, "assistant", finalResp.Content) 存入数据库。

如果是普通闲聊（没有工具调用），也要把 resp.Content 存入数据库。

目的：确保下一次对话时，AI 能回忆起来它自己上一句说了啥。

四、踩坑与逻辑复盘
假 UserID：

目前代码里写死了 userID := uint(1)。真实业务中，这个 ID 应该从 JWT Token 中解析出来，传给 Handler。

上下文爆炸风险：

大模型的上下文长度是有限的（比如 64K）。所以 GetRecentChats 必须加上 Limit(10) 限制。如果未来需要长期记忆，需要引入向量数据库（RAG）做语义检索，而不是单纯地拉取所有记录。

验证效果：

发送第一句“我叫李四，爱吃苹果”。

重启服务（Ctrl+C 后重新 go run）。

发送第二句“我叫什么？爱吃什么？”。AI 完美回答，证明数据持久化成功。
